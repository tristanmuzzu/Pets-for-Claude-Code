# v0.8.0: it runs on Linux, and you can download it

Until now the Releases page had a Windows installer and a note saying Linux was
untested. There are now six files on it, and the three new ones are a `.deb`, a
`.rpm` and an `.AppImage`.

## Install

**Ubuntu, Debian** — `sudo apt install ./Pipsqueak_0.8.0_amd64.deb`

**Fedora, RHEL, openSUSE** — `sudo dnf install ./Pipsqueak-0.8.0-1.x86_64.rpm`

**Anything else** — `chmod +x` the `.AppImage` and run it. Keep it somewhere
permanent first; see below for why that matters more than it usually does.

Built on Ubuntu 22.04. The highest symbol the binary asks for is `GLIBC_2.34`,
measured on the released `.deb`, so Ubuntu 22.04, Debian 12, Fedora 35 and
anything newer are fine. Windows is unchanged.

## The AppImage would have registered a path that stops existing

An AppImage is a self-mounting archive: the running program is
`/tmp/.mount_PipsqXXXXXX/usr/bin/pipsqueak`, and that mount is unmounted the
moment the app quits. Both the Claude Code hook command and the autostart entry
were `current_exe()`, so both would have recorded it.

That is a particularly nasty shape of broken. Everything works — hooks fire,
cards appear, **Check my setup** is green — right up until the first time you
close the pet. After that Claude Code spawns a path that no longer exists, on
every hook, forever, and nothing anywhere says so.

The launcher exports `APPIMAGE` with the path of the `.AppImage` file itself,
which is the thing that actually persists. Everything that records a path for
something else to run later now goes through `desktop::own_program()`, which
prefers it. Which is also why the file wants a permanent home: if you move it
after setup, run `pipsqueak install` again from the new location.

## Autostart, on the platform that had none

`set_autostart` returned the string `"autostart is only implemented on Windows
so far"`, while the README promised that an overlay which does not survive a
reboot is not one. It now writes `~/.config/autostart/pipsqueak.desktop` — the
XDG spec, so GNOME, KDE, XFCE and the rest all read it — with the `Exec=`
quoting the spec requires, so an AppImage living under `~/My Apps/` still
starts. `pipsqueak autostart off` removes the file and is remembered.

## Saying true things on the machine you are actually on

- The welcome panel and the tray menu said **Start with Windows** on a Linux
  desktop. The phrase now comes from the backend, which knows.
- The hotkey reported that *every candidate chord is already taken*, which
  would send you hunting for a program that is not there. Wayland has no
  registration for an ordinary application to lose. It now says so, and points
  at `pipsqueak control toggle`, which your desktop's own keyboard settings can
  bind — that is the supported way to do this on Wayland, and it works whether
  or not the pet is already running.
- `same_program` folded case and slash direction on every platform. That is
  right on Windows and wrong on a case-sensitive filesystem, where it would
  call a stale autostart entry healthy.

Two things are genuinely missing on Linux and are written down rather than left
to be discovered: there is no global hotkey, and the pet does not follow your
cursor with its eyes, because a Wayland client may not ask where the pointer is
unless it is over the window — which a click-through window never is.

## CI now runs on both platforms, which found things immediately

Every Linux fix in this repository so far compiled and passed perfectly well on
Windows. `ci` and `release` now run a Windows + `ubuntu-22.04` matrix, with the
same tests, clippy and rustfmt gates on each. `ubuntu-22.04` rather than
`ubuntu-latest` deliberately: glibc is forward-compatible and not backward, so
the runner's version is the floor for everyone who downloads the result.

Switching it on found a `needless_return` and seven constants that are dead
once the hit-test loop is compiled out — and one thing worth its own paragraph.

**The sprite check could not pass on two platforms at once.** It was `npm run
sprites && git diff --exit-code public/pets`, which compares files. A PNG ends
in a deflate stream, and two zlib builds handed identical pixels emit different
bytes for them. Regenerating the atlases on Linux produced files differing from
the committed ones by about 150 bytes and by exactly zero pixels. `npm run
check:sprites` now decodes both sides and compares the RGBA, then puts the
committed bytes back. A hand-edited sprite still fails, which is the entire
point of the check.

The release workflow also stopped letting both builds find-or-create the
release by tag. Two runners starting within a second of each other can both
decide it is missing, and a tag that produces two drafts puts half the
platforms on the wrong one. `check` opens the draft and hands its id to both.

## Verified

On real hardware, Ubuntu 26.04 / GNOME 50 / Wayland, against the bundles this
release is built from:

- deb, AppImage and rpm all build.
- The AppImage registers **its own path** into a sandboxed `settings.json`, not
  the `/tmp` mount. This is the bug above, tested rather than reasoned about.
- `autostart on` writes the desktop entry, `status` reads it back, `off`
  removes it and leaves nothing behind.
- The deb's binary installs 15 hooks and removes all 15, backing up
  `settings.json` both times.
- The sprite check catches a single flipped pixel and reports its coordinate.
- clippy and rustfmt clean for the Linux **and** the Windows target; 100 Rust
  tests, 34 JavaScript tests.

Not verified: X11 (the input-shape mechanism is X11's own, so it should be no
worse, but nobody has sat in front of it), and macOS, which still builds and
still has no autostart implementation.
